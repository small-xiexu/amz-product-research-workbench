# 自有评论插件对接方案

更新日期：2026-06-15

## 结论

目标对接方式升级为第三档：**AI 在 Web 工作台里判断何时需要抓评论，生成 ASIN 批次，运营确认后由 Chrome 评论插件自动领取任务、慢速采集并回传评论 JSON，后端自动触发 VOC 分析。**

文件导入仍保留为 fallback：

`评论插件导出 Excel + HTML AI 报告 -> 选品系统读取 Excel -> 生成 review_voc_package -> 合并到重点候选深挖`

不读取 Chrome Storage，也不让选品系统直接控制 Amazon 页面。插件继续负责浏览器登录态、慢速采集、验证码/登录暂停和页面结构适配；Web 工作台负责创建任务、接收结果、触发 `review-voc-analysis` Skill。

## 为什么这样接

| 方案 | 结论 | 原因 |
|---|---|---|
| 插件领取任务并回传 JSON | 目标方案 | 自动化程度最高；保留插件对 Amazon 登录态和风控节奏的控制 |
| 读取插件 Excel | fallback | 字段稳定、可追溯；适合任务接口未完成或插件离线时手动导入 |
| 读取 HTML AI 报告 | 辅助 | 报告适合人读，但不能作为结构化证据主来源 |
| 读取 Chrome Storage | 不做 | 和扩展 ID、浏览器状态、运行时强绑定，稳定性差 |
| Web 后端直接抓 Amazon | 不做 | 无法复用用户登录态，风控和验证码处理风险更高 |

## 第三档交互流程

1. 候选池或深挖阶段产出 `next_review_voc_asins`。
2. AI 根据 Skill 判断评论样本必要性，给出 ASIN 批次和选择理由。
3. Web 左侧出现评论任务卡，运营确认“开始抓评论”。
4. 后端创建 `review_task`，状态为 `queued`。
5. 评论插件轮询 `GET /api/review-tasks/pending` 领取任务。
6. 插件按站点和 ASIN 打开 Amazon 评论页慢速采集。
7. 插件上报进度：当前 ASIN、站点、已采集条数、暂停原因。
8. 插件完成后回传评论 JSON。
9. 后端生成 `review_voc_package`，触发 `review-voc-analysis` Skill。
10. Web 展示 VOC 痛点、亮点、改品建议和证据摘要。

## 评论任务状态

| 状态 | 含义 | 处理 |
|---|---|---|
| `draft` | AI 已生成建议，等运营确认 | Web 展示 ASIN 批次和理由 |
| `queued` | 已确认，等插件领取 | 插件轮询领取 |
| `running` | 插件正在采集 | Web 展示进度 |
| `paused_login` | Amazon 需要登录 | 提示运营处理登录后继续 |
| `paused_captcha` | 遇到验证码/验证页 | 暂停，不绕过验证 |
| `completed` | 评论 JSON 已回传 | 后端生成 VOC 包 |
| `failed` | 采集失败 | 展示失败原因，可重试 |
| `analyzed` | VOC 分析完成 | 进入深挖/报告链路 |

## 接口草案

| 接口 | 调用方 | 作用 |
|---|---|---|
| `POST /api/sessions/{session_id}/review-tasks` | Web/AI | 创建评论采集任务 |
| `GET /api/review-tasks/pending` | 插件 | 获取可领取任务 |
| `POST /api/review-tasks/{task_id}/claim` | 插件 | 锁定任务，避免多插件重复跑 |
| `POST /api/review-tasks/{task_id}/progress` | 插件 | 回传进度和暂停状态 |
| `POST /api/review-tasks/{task_id}/reviews` | 插件 | 回传评论 JSON |
| `POST /api/review-tasks/{task_id}/analyze` | 后端/AI | 触发 VOC 分析 |

## 插件需要改造的点

| 文件 | 改造 |
|---|---|
| `manifest.json` | 增加工作台后端地址的 host permission，例如 `http://127.0.0.1:8000/*` |
| `popup.js` | 增加“连接工作台/任务模式”配置；保留手动输入 ASIN |
| `background.js` | 新增轮询任务、claim、progress、reviews 回传逻辑 |
| `content.js` | 保持页面采集逻辑；遇到登录/验证码时上报暂停状态 |

插件已有 `导出 JSON（工作台）` 雏形，可复用其字段映射作为回传 JSON 基础。

## 插件已确认导出格式

Excel：

- 文件名示例：`B07R56CBWX-multi-2026-06-07.xlsx`
- Sheet：`评论数据`
- 规则：只导出 Verified Purchase 评论
- 多 ASIN / 多站点：合并在同一个 Sheet，通过 `ASIN` 和 `站点` 区分

关键字段：

| 字段 | 用途 |
|---|---|
| ASIN、站点 | 对齐竞品池和候选方向 |
| 评论ID、评论链接 | 证据追溯 |
| 评论日期、评星、情绪 | 时间、口碑和差评结构 |
| Helpful数量、是否有买家实拍、图片数量 | 权重和证据强度参考 |
| 评论产品的属性、颜色、尺寸 | 变体和细分问题 |
| 英文标题、英文评论、标题中文翻译、评论中文翻译 | VOC 分析主文本 |

HTML AI 报告：

- 文件名示例：`B07R56CBWX-multi-2026-06-07-report.html`
- 用途：辅助阅读痛点、亮点、改品建议
- 边界：不能替代 Excel 证据；正式结论必须能回到评论 ID

## 推荐落盘位置

评论插件导出的原始文件，建议和卖家精灵导出分开存放，仍然放在项目根目录下。

推荐结构示例：

```text
/Users/sxie/Documents/亚马逊/amz-product-research-workbench/
  评论插件导出_刮窗器_20260608/
    B07....xlsx
    B07....-report.html
```

如果同一轮有多个 ASIN 或多站点评论文件，也尽量都放进这个目录，工作流直接传目录里的一组文件路径即可。

## 进入选品系统的规则

1. Excel 是结构化主来源。
2. HTML AI 报告只作为参考，不直接作为强证据。
3. 每个痛点和亮点必须保留评论 ID、ASIN、评分、日期、证据片段和评论链接。
4. 多 ASIN 数据优先用于品类共性痛点；单 ASIN 数据优先用于竞品短板。
5. 只有候选方向进入深挖后才接评论插件，不在候选池初筛阶段要求评论数据。
6. 评论插件的输入建议是候选池筛出的 ASIN 批次，通常先取 10-20 个，优先包含 Top10 标杆、新品和争议竞品，不是只取 3-5 个孤立样本。
7. 第三档接口完成后，插件回传 JSON 是主来源；Excel 导入降级为 fallback。
8. 遇到登录、验证码、访问限制时必须暂停并让运营处理，不绕过验证。

## 合并到深挖报告

把 `review_voc_package` 合并进 `research_package`：

- `review_sources`：记录插件 Excel 和 HTML 来源
- `voc_analysis`：写入痛点、亮点、场景、改品机会
- `opportunity_hypotheses`：追加可追溯的 VOC 证据
- `status_card`：把评论风险纳入继续/观察/放弃判断

命令：

```bash
python3 scripts/build_research_package_from_candidate.py \
  <candidate_pool.json> \
  <research_package.json> \
  <candidate_id> \
  --voc-package <review_voc_package.json>
```

合并后，主报告和 Excel 会新增评论 VOC 摘要、痛点证据、亮点证据和改品机会。
