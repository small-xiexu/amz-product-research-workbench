# 1688 供应链采集方案

## 结论

先做“浏览器插件 + 本地标准化 + 可选 MCP 接口”，不要先做纯 MCP。

原因很简单：1688 的关键不在算术，而在登录态、中文搜索词、详情页结构、价格口径和证据留存。插件最适合做这些脏活累活，MCP 更适合做后面的统一调用层。

这个方向的实现形态，建议直接对齐你现有的 [亚马逊评论慢速采集助手](/Users/sxie/Documents/亚马逊/amz-review-harvester/README.md)：页面里采集，落地成结构化 JSON / Excel，再交给工作台分析。

## 目标

- 只看 `1688.com` 中国站
- 只认人民币 RMB / CNY
- 不是搜“便宜货”，而是搜“改进款”和“可替代方案”
- 让 Amazon VOC 痛点能映射到 1688 货源
- 输出能复核的证据，不只输出一堆链接

## 不做什么

| 不做 | 原因 |
|---|---|
| 不用 Alibaba 国际站 USD 替代 1688 | 口径会跑偏 |
| 不做无头抓取绕过登录 | 稳定性差，且不适合当前阶段 |
| 不把 MCP 当主采集器 | 1688 的结构变化和登录态更适合浏览器插件 |
| 不在初筛阶段强求完整利润表 | 先找得到货，再算得清账 |

## 推荐架构

| 层 | 职责 | 说明 |
|---|---|---|
| 浏览器插件 | 搜索、翻页、详情页抓取、证据截图 | 保留手动登录态，像评论采集器一样工作 |
| 本地标准化层 | 去重、清洗、统一字段、打标签 | 生成可入库的 JSON / Excel |
| 供应链适配层 | 统一成候选供应商结构 | 方便接到现有 `candidate_pool` / `research_package` |
| 工作台 | 展示候选、人工确认、回填报告 | 作为决策中心，不直接依赖页面抓取 |
| MCP 接口 | 以后再加 | 只负责查询和调用，不承担主采集逻辑 |

## 输入应该是什么

不要直接拿英文产品名硬搜 1688。更好的输入是三类：

1. Amazon VOC 痛点
2. 候选方向
3. 供应链约束

例如宠物牵引绳这类，优先把 VOC 翻成采购词：

- 免手持牵引绳
- 腰带牵引绳
- 弹力遛狗绳
- 双把手遛狗绳
- 反光遛狗绳
- 跑步遛狗绳
- 带腰包牵引绳

## 采集对象

插件至少要抓两层：

| 层级 | 抓什么 | 作用 |
|---|---|---|
| 搜索结果页 | 标题、价格、MOQ、商家名、发货地、销量线索、链接 | 快速筛掉明显不相关项 |
| 详情页 | SKU 属性、定制能力、一件代发、现货、包邮、图片、证据截图 | 判断是不是改进款、能不能做 |

## 最小字段

| 字段 | 说明 |
|---|---|
| 查询词 | 这条货源是用什么词搜出来的 |
| 标题 | 1688 原始标题 |
| URL | 必须可回溯到 `*.1688.com` |
| 价格区间 | 只保留 RMB / CNY |
| 起订量 | MOQ |
| 商家名 | 供应商名称 |
| 发货地 | 判断履约和供应稳定性 |
| 是否现货 | 快速判断能否试做 |
| 是否支持定制 | 判断改款空间 |
| SKU 属性 | 颜色、尺寸、组合、材质 |
| 证据截图 | 防止后面链接失效 |
| 采集时间 | 方便复核时效 |

## 评分规则

先规则筛，不先上大模型。

| 维度 | 看什么 |
|---|---|
| 改进匹配度 | 是否直接对应 Amazon VOC 痛点 |
| 价格带 | 是否落在目标采购区间 |
| 供应稳定性 | MOQ、发货地、现货/定制、商家信息完整度 |
| 改款空间 | 结构上有没有明显升级点 |
| 证据完整度 | 是否有 URL、截图、详情页、更新时间 |

建议优先保留三类候选：

1. 明显能解决核心痛点的改进款
2. 价格带明显可做的同款 / 近似款
3. 结构升级后能形成差异化的款

## 和现有工作台怎么接

建议接到现有这几层里：

- `selection_brief.json`：增加供应链偏好和禁区
- `candidate_pool.json`：增加 `supply_chain_candidates`
- `research_package.json`：增加 `supply_chain_signals`
- 最终报告：增加 `1688 供应链验证` 小节

如果后面做 MCP，也不要另起炉灶，直接复用这套标准化结果。

## 分阶段推进

| 阶段 | 交付 |
|---|---|
| 第 1 阶段 | 手工搜词 + 导出结果 + 统一字段 |
| 第 2 阶段 | 浏览器插件化，自动抓搜索结果和详情页 |
| 第 3 阶段 | 本地标准化 + 候选评分 + 证据留存 |
| 第 4 阶段 | 接入工作台，和 VOC / 候选池联动 |
| 第 5 阶段 | 再考虑 MCP 包装成统一查询入口 |

## 验收标准

- 只看 1688 中国站，不混国际站
- 价格字段全是 RMB / CNY
- 每条候选都能回溯到 URL 和截图
- 能把 Amazon VOC 痛点映射成采购词
- 能输出“改进款候选池”，不是只输出一堆搜索结果

## 一句话版本

1688 这块最好的做法，不是找一个更大的 MCP，而是先做一个像你现有评论采集器那样稳的 1688 插件，再把结果喂给工作台做改款筛选。
